### Phase 1 findings: `FC3.dll` and the Domino boxes (2026-10-24)

- **Correction:** the box code IS Lua. A graph loads boxes with `cbox:RegisterBox("Domino/System/Player/GetLocalPlayer.lua")`; each box is a Lua file in the same archives, with a reflection header (`-- DOMINO REFLECTION BOX START`, `<Display>`, `<ControlIn>`, `<DataOut>`). The earlier claim "box code is native in `FC3.dll`" was wrong. Only the Lua globals the boxes call (for example `GetLocalPlayerId()`) are native.
- **File names are hashes of box names.** Name hash = CRC-64/ISO (reflected, polynomial 0xD800000000000000, init 0, no final xor, table = `Gibbed.Dunia.FileFormats.Hashing.CRC64`) over the **lower-cased path with backslashes**. Check: `domino\system\player\getlocalplayer.lua` gives `9716CA537E634631`, which exists in `fc3_main\__UNKNOWN\unknown\` and `multicommon\__UNKNOWN\unknown\` (782 bytes, identical in both, MD5 `5E8EFF68D5AF85A2E7F849D233170134`). Also `domino\system\getscriptentity.lua` gives `235DF3F86557C6FA`. Files without extension in `unknown\` are the boxes.
- **Name lists exist after all:** the resource manifests `__UNKNOWN\misc\*.root.xml` (for example `fc3_main\__UNKNOWN\misc\7215F999AEACCD55.root.xml`, `multicommon\__UNKNOWN\misc\7FFFAC13D814F0C8.root.xml`) list `<CDominoBoxResource ID="Domino/...lua">`, textures, materials and more. Hashing these IDs names every file. Not done yet.
- **The `GetLocalPlayer` box is trivial:** `function GetLocalPlayer:In() self.LocalPlayer = GetLocalPlayerId(); Out(self) end`. So the single-player graphs reach the local player through the Lua global `GetLocalPlayerId`, and an override box file in our own archive could change it for 1484 call sites in `fc3_main`.
- **`FC3.dll` (x86, Ghidra 12.1.4, via REA):** string `GetLocalPlayerId` at `0x11fbdcc4` has two references. (1) `0x111ce912` inside `FUN_111cdb00`, the registration table of **console commands** (`GetLocalPlayerId` -> `FUN_111cb980`, which only formats a string, so it is not the Lua function; the same table has `TeleportToCurrentObjective`, `SetHealth`, `HitMe`, `GetCurrentPrimaryBuddy`, `SetNoWeaponMode`, `ActivateChallenge`, `CompleteChallenge`). (2) `0x11b1b5c4` inside `FUN_11b1b4e0` (4442 bytes), probably the registration of the **Lua global**. The string `Game:GetLocalPlayerId(%%)` at `0x11fba634` is referenced from `0x111ef365` (a very large function). Not decompiled yet.
- Not found in `FC3.dll` as strings: `PlayerCount`/`GetPlayerFromSlot` (only `m_playerCount: %i` at `0x11fafae8` and `MultiCaptureBarPlayerCount` at `0x12026c84`) and `Domino/System/Player`. Box names are not in the DLL; `PlayerCount` is a Lua box in `multicommon`.

### Phase 1 findings: the player service is a network object (2026-10-24)

- `S` is the component **`CFCXPlayerService`**. `FUN_1039e1f0(container)` walks a component array (`container+8`, count `container+0xc`) and returns the entry whose type (vtable slot +4) matches the static type from `FUN_1039e0d0` (`&DAT_12860b80`, name `CFCXPlayerService`); the last index is cached in `DAT_1217a7d4`. The container is `*(DAT_12804acc+0x68)`; `DAT_12804acc` has 4529 references (a central game/services object).

Other strings: `IPlayerService`, `CPlayerService`, `NetDiscoveryGroup.PlayerService`. Net registration code: `FUN_11839b60`, `FUN_10468480`.

### Tools: archive packer and an unpacker fix (2026-10-24)

- **Archive list the engine loads** (`0x120701c4`): `patch.dat`, `patch_%lang%.dat`, `patch_sound_%lang%.dat`, `common.dat`, `sound.dat`, `sound_%lang%.dat`, `ige.dat`, `igepatch.dat`, `shadersobj.dat`, `worlds/fc3_main/fc3_main{,_%lang%,_vistas}.dat`, `worlds/multicommon/multicommon{,_%lang%,_vistas}.dat`; also strings `_2.dat`, `subfat_%s.fat`, `mergedBigFileName` (meaning unknown). So a mod ships a rebuilt `patch.dat/fat` = the vanilla patch content plus our files (this is also how the owner's skip-cutscenes mod worked).
- **FAT v9 layout (checked on the shipped `patch.fat` and `common.fat`):** 24-byte header `FAT2`, version 9, flags `0x301` (platform 1 = Windows, compression version 3), `u0C = u10 = 0`, entry count; 20-byte entries sorted by hash; then 8 zero bytes. Uncompressed entries have scheme 0, `UncompressedSize = 0` and the size in `CompressedSize`. Data offsets are not aligned in shipped files.
- **Packer:** new project `Gibbed.FarCry3.Pack` (`bin_fc3\Gibbed.FarCry3.Pack.exe output.fat input_dir`, stores files uncompressed). Changes in Gibbed: `BigFileV2.Serialize` implemented for v9 only; `Pack` takes default version and compression version (9, 3 for FC3); files under `__UNKNOWN` now keep 16-digit hashes (the old code cut them to 8 digits, which only fits 32-bit hashes). LZO compression is still not implemented upstream (not needed).
- **Unpacker bug, fixed:** the unpacker read uncompressed entries with `UncompressedSize`, which is 0 in FC3, so every uncompressed file was written **empty** into `__UNKNOWN\null\`. Affected in the Phase 1 output: `patch` 4 (two `.bik` videos of 136 MB and 63 MB, two materials), `common` 429, `multicommon` 17108, `fc3_main` 11799 files, and 16 files in `named\`. Fixed in `EntryDecompression.cs` and the type guess in `Unpack.cs`; all four archives were unpacked again with the fix: `patch` 427, `common` 3099, `multicommon` 122255, `fc3_main` 64354 files, no empty files; `names.tsv` and `named\` rebuilt (45045 names, 0 empty text files). Helper scripts (name hashing, FAT dump, re-unpack): `scripts\`.
- **Round-trip check:** vanilla `patch.fat` unpacked, packed again and unpacked again: 427 of 427 files identical (MD5).
- Build needs the local NuGet cache (see below for the scubrah mod and version 1.05): `$env:NUGET_PACKAGES='E:\FarCryCoop\Data\nuget'`, `dotnet build ... --source E:\FarCryCoop\Data\nuget` (`env.ps1` does not set it). Patch file: [docs/gibbed-dunia-fc3.patch](docs/gibbed-dunia-fc3.patch).

- **Lesson (2026-11-02):** registration routines reached only through the CRT initializer are invisible to a
  caller scan, and handler/callback pointers passed in registers are invisible to `code_refs()`. The
  remaining handle on the `-exec` consumer is the 180-byte session-parameter struct at
  `FC3.dll 0x11a8d0db` plus the session object's `+0x98` field — probe those layouts next.
- **ExecLines container is a global singleton (`FC3_d3d11.dll`).** A raw byte scan of `.text` for the
  disp32 `24 94 82 12` (0x12829424 in little-endian) gives **17 502 access sites**, overwhelmingly
  `8b 0d` (`mov r32,[g]`) pairs ~12 bytes apart — the `mov ecx,[g]` / `call fn` idiom — i.e. this global
  is the manager object used as `this` by thousands of calls; only two construction-shaped writes
  (`c7 05` at `0x1178846e` and at `0x118e82fd`). Lesson recorded the hard way: a VA is written in
  **little-endian** in the image (`0x12829424` → `24 94 82 12`); searching for the reversed byte order
  (or computing blob offsets with VA arithmetic instead of `file offset − section raw pointer`) produces
  false "0 matches" results.
- **Static dead end for the `execLines` consumer (2026-11-02, `FC3_d3d11.dll` 1.06):** the lazy-init
  thunk at function `0x118e82d0` is the container's Meyers-singleter accessor — `test byte ptr
  [0x128ac410], 1` / `or dword ptr [0x128ac410], 1` / `push 0; mov ecx, 0x128ac3f4; call 0x106c4b40` /
  `push 0x11bb98c0; call 0x1070085d` / `mov al, 1; mov dword ptr [0x12829424], 0x128ac3f4; ret` — and
  `0x11bb98c0` is an atexit-registered destructor thunk (`mov ecx, 0x128ac3f4; jmp 0x106c4b70`), sibling
  `0x11bb98d0` for the next global. Session-op field names are registered on first use by lazy thunks
  (`0x11348230` guard `[0x1282a60c]` → `call 0x11347c60` guard `[0x1282a607]` → `push <name>; push <size>`

  `0x11bc8a80`..`0x11bc8ad0` shaped `b8 <slot> ; e9 <jmp 0x10004d70>`. Conclusion: a static scan will not

## Launch bridge measured (2026-11-02, `scripts/fc3_launch_probe.py` + `scripts/fc3_upc_probe.py`)

The stub does **not** run the game directly, and it does **not** silently discard the extra arguments — it
hands them to Ubisoft Connect. Observed process tree from `TestFC3/bin/farcry3_d3d11.exe -language=Russian
-quickstartup -host fc3_main -login coop1 -coop`:

1. stub pid 25472 exits with code 0 after ~6 s.
2. new process `C:\Program Files (x86)\Ubisoft\Ubisoft Game Launcher\upc.exe`, pid 18080, command line with
   **every argument preserved**: `-upc_uplay_id 46 -language=Russian -quickstartup -host fc3_main -login
   coop1 -coop -upc_desktop_mode -upc_game_starter`.
3. upc then starts the **canonical install** stub and drops the quick-launch arguments:
   `"H:/Uplay/Far Cry 3/bin/farcry3_d3d11.exe" -language=Russian` (pid 31948, ppid 2068).

⇒ the forwarding path is `upc.exe -upc_uplay_id <id> <switches> -upc_desktop_mode -upc_game_starter`; the
drop happens only in upc's final game start. A trampoline in front of `TestFC3/bin/farcry3_d3d11.exe` that
calls `upc.exe -upc_uplay_id <id> <args> …` is the candidate for option (b) — it needs the test copy's **own**
uplay id (id 46 resolves to the store install) and the canonical game must not already be running (pid 31948
made a later `upc` relaunch exit 0 within 6 s — the `OpenMutexA("FarCry3Instance")` single-instance guard).

Also verified on 1.06: `FC3_d3d11.dll` imports **only `ShellExecuteA`** (`SHELL32.dll`, thunk `0x11be1720`, 2
call sites `0x10c13882` and `0x10fc2382`, both shaped `6A 01 6A 00 6A 00 68 <url> 68 <verb> 6A 00
FF 15 20 17 BE 11 C3`; verbs `open`/`reopen`/`read` at `0x11f5f210`), and both URLs are marketing links —
`http://shop.ubi.com/store/ubiemea/html/pbPage.generic-Far-Cry-3-303-other…` at `0x1209f220`,
`http://store.steampowered.com/app/220240` at `0x1202fcec`. `FC3_d3d11.dll` imports **no `ShellExecuteEx`
and no `CreateProcess`**, so the earlier working note claiming "ShellExecuteEx at `0x11a4b404`" was a mis-read
of a direct call inside a 1181-byte function (`0x11a4b…`..`0x11a4b4c5`, 30 direct calls, 0 indirect calls).
The re-exec is performed by the launcher/UI layer through Ubisoft Connect, not by a `CreateProcess` in the
game DLL.

**Conclusion:** quick-launch co-op is impossible on this build without either (a) a 1.05 DRM-free executable,
or (b) a launcher bridge — a stub/UPC trampoline that makes Ubisoft Connect start **our own** copy with the
quick-launch arguments (the argument forwarding itself is now measured, above). Both need a decision from the
owner.
