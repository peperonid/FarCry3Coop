# План R2 — подставить LAN-провайдер сессий вместо `_RdV` в Far Cry 3 (PC 1.05/1.06, `FC3_d3d11.dll` md5 46bcc097)

Отдельный план проекта, продолжение NOTES 28du-28dv. Только статическая разведка (capstone по
сырому DLL; копия проекта в Ghidra — `-noanalysis`, а полный 40 МБ headless-переанализ в текущем
окружении непрактичен). Документ перечисляет конкретные якоря для патча и поэтапный план с
верификационными гейтами и критериями остановки. Все адреса — VA образа файла (добавлять базовый
адрес модуля в рантайме; ASLR включён). Это проект реверс-инжиниринга + кода, НЕ переключатель в конфиге.

## 0. Цель и базовые факты

Цель: заставить FC3 хостить/джойнить co-op-сессию карты кампании по LAN/loopback (Storm), чтобы
2+ человека могли играть БЕЗ мёртвого сервиса матчмейкинга Ubisoft RendezVous.

Базовые факты из прошлой работы (NOTES 28dm-28dv):
- На PC у FC3 прописаны ТОЛЬКО провайдеры матчмейкинга/сессий RendezVous (`_RdV`; кампания никогда
  не работала как сетевая; лобби co-op Ubisoft мертво онлайн; офлайн игра ждёт живого бэкенда
  «online-service connected + party/session»).
- Дев-путь командной строки (`-host -coop` / `-client -ip`) НЕ срабатывает на 1.06-релизе при прямом
  запуске (28du).
- Мультиплеер/Storm из 1.06 НЕ вырезан: базовые (не-RV) классы сессий и LAN-примитивы Storm
  присутствуют в бинарнике.

Вся теза R2 держится на последнем пункте: **не-`_RdV` машинерия сессий существует; надо заставить
игру выбрать и запустить её.**

## 1. Конкретные якоря (эта сессия + хаб)

Классы сессий/провайдеров (RTTI/логи строк + код, который их использует):
| Символ | VA строки | ссылка из |
|---|---|---|
| `CSessionCreateOperation` (база, не-RV) | 0x11523fa8 | 0x10425885 (в заводе ~0x10425822) |
| `CSessionCreateOperation_RdV` | 0x11527a78 | 0x1044b650 (в заводе ~0x1044b2cb) |
| `CSessionJoinOperation` (база, не-RV) | 0x11524030 | 0x10425961 (тот же базовый завод) |
| `CSessionJoinOperation_RdV` | 0x11527b88 | 0x1044bfd4 (тот же RdV-завод) |
| `SessionSearchIPOperation` (IP-сессия) | 0x11524015 | (только RTTI/лог) |
| `MatchmakingProvider` (база) | 0x11589218 | (только RTTI/лог) |
| `MatchmakingProvider_RdV` | 0x1158b43d | (только RTTI/лог) |
| `RendezVousBackEndServices_native.cpp` / `RendezVousGuest...` | 0x115265f9 / 0x11526901 | (auth-бэкенд) |

Ключевой структурный вывод: завод базовых операции (0x10425822) и завод `_RdV`-операций (0x1044b2cb)
— это **виртуальные методы**; `callers_of()` находит ноль прямых `E8`-вызовов, поэтому провайдер
выбирается тем, **какой объект-провайдер инстанцируется и устанавливается**, а не веткой вызова.
Это единственный якорь, который мы ещё НЕ закрепили (нужен RTTI/vtable-анализ).

Параметры сессии (из PR хаба + нашей ссылки):
| Параметр | VA строки | регистрируется в |
|---|---|---|
| `MatchMakingEnabled` | 0x11561628 | ~0x1061e581 (ссылка 0x1061e633) |
| `NetEngineType` (id 0x3c) | отмечен хабами | та же функция схемы параметров |
| `SearchIdAddress`, `JoinSessionId`, `SessionType`, `PlaylistId` | отмечены хабами | там же |

Путь командной строки / режима (28dv):
- маппер `sessionTypeByName` (пролог 0x107ab377): `-coop` -> enum режима из *[0x1171a99c];
  похоже на `-host` -> *[0x1171a9a4]; остальные 0x1171a994/0x1171a98c.
- стартовый парсер CLI/ini ~0x100044d0-0x10004830 кладёт режим/флаги в глобалы 0x117f5d84..0x117f5dd4.
- Storm LAN: `storm::echo::session`, `storm::echo::lan`, `BroadcastLanDiscovery2`, порты 9000-9004.

## 2. Стратегии патча (кандидаты, по ожидаемой tractability)

Стратегия A — **переключить выбор провайдера на базовый (не-RV).**
Найти, где игра инстанцирует/устанавливает `CGameMatchmakingProvider_RdV` (и `_RdV`-заводы
create/join), и поставить базовый провайдер (или заставить `_RdV`-завод форвардить на базовый
0x10425822). Если базовые операции строят Storm LAN-сессию — это чистейший выигрыш. Нужно: обход
RTTI для поиска vtable `_RdV`-провайдера и места его конструкции.

Стратегия B — **переопределение слотов vtable завода create/join** (shim).
Вместо поиска места установки — хукнуть виртуальные слоты, чтобы `_RdV`-объект возвращал БАЗОВЫЕ
`CSessionCreateOperation` / `CSessionJoinOperation` (строит 0x10425822). Наш shim уже делает vtable-
трамплины; добавить vtable провайдера/менеджера сессий в трейсер (читать `vtable_rva` объекта), затем
детурить два слота.

Стратегия C — **принудительно LAN/direct-параметры сессии.**
Задать при создании `MatchMakingEnabled=0` и `NetEngineType=LAN` (функция схемы параметров
~0x1061e581), плюс `SearchIdAddress`/`JoinSessionId` для прямого джойна. Дешевле всего попробовать,
но, вероятно, недостаточно, т.к. объект-провайдер всё ещё `_RdV` (по хабам), и параметры могут
игнорироваться. Быстрый зонд, не фикс.

Стратегия D — **локальный эмулятор RendezVous** (другая опция «поправить join-путь»).
Оставить `_RdV`-провайдер, но отвечать на его login/ticket/session RPC локальным RV/PRUDP-сервером
(наша заготовка `scripts/rv_server`). Наивысшая точность, но это большой проект эмуляции
(auth + party + ticket + GameSessionKey), а не замена провайдера. Вне объёма R2.

## 3. Поэтапный план с гейтами

Этап R2-1 (анализ, ~1-2 сфокусированные Ghidra-сессии): полный авто-анализ `FC3_d3d11.dll` в
нормальной Ghidra-сессии (дать 20-40 мин; больший REA_GHIDRA_STARTUP_TIMEOUT_MS, запуск по-настоящему
отсоединённо с логом в файл). Получит: RTTI `CGameMatchmakingProvider_RdV` + базового
`MatchmakingProvider` + двух `_RdV`-заводов; vtable онлайн-менеджера сессий (глобал 0x11f07e48) и
место конструкции/установки провайдера. ГЕЙТ: названное место конструкции/установки `_RdV`-провайдера.
Критерий остановки: если `_RdV`-провайдер жёстко прописан без виртуального шва/регистрации и базовый
провайдер не может работать отдельно — R2-A/B мертвы, и LAN-пути без полной RV-эмуляции нет (-> D).

Этап R2-2 (спайк замены провайдера, shim): реализовать стратегию B — трассировать vtable
менеджера/провайдера сессий, детурить слоты завода create/join на базовый завод (0x10425822).
ГЕЙТ (только боты, по AGENTS «тестировать ботами, не владельцем»): один запущенный инстанс выходит
на РЕАЛЬНУЮ Storm listen-сессию (Storm занимает порты 9000-9004 с активной сессией, НЕ тот
праздный меню-UDP:9000, что мы уже видели) и пишет в лог созданную сессию. Гейт не пройден =>
провайдер всё ещё гейтится выше.

Этап R2-3 (джойн второго инстанса): запустить инстанс B клиентом с direct-join-параметрами / путём
`SessionSearchIPOperation` на LAN-адрес A; наблюдать добавление игрока Storm
(`storm::echo::session::resultEvent::AddPlayer`) и заполнение 2 слотов в `CFCXPlayerService`.
ГЕЙТ: два игрока в одном мире с синхронизацией движения (хаб подтверждает слот 1 через
`GetPlayerInSlot` / `CoopTeleportPlayer` Lua). Критерий остановки: если джойны не формируют Storm-
сессию даже с базовым провайдером, LAN-путь в релизе реально не работает.

Этап R2-4 (прогон кампании + QA синхронизации): когда 2 игрока в карте — проверить, что сюжетные
скрипты кампании рассчитаны на co-op (хаб отмечает скрипты лишь «частично co-op-aware»; есть
`GRI_Coop_*.lua` + co-op сущности спавна). Это неисследовано и может потребовать патчей скриптов/данных.
ГЕЙТ: автотест 2 ботов с харнессом desync/ownership (хабовские `tools/` chaos/ownership/fuzz) на
честном уровне QA.

## 4. Объём / риск

- R2-1 анализ: дни, средний риск (хрупкость Ghidra в этом окружении — реальное трение; запускать
  отсоединённо с большими таймаутами).
- R2-2 замена провайдера: дни-недели, ВЫСОКИЙ риск (якорь выбора провайдера ещё не закреплён; сам
  базовый провайдер может при конструкции предполагать онлайн-сервис).
- R2-3 джойн: недели, ВЫСОКИЙ риск (не проверено, что базовый/SessionSearchIP-путь вообще куда-то
  подключён в релизе 1.06; вероятно, тоже упрётся в тот же гейт «online-service connected» выше по
  стеку, как в 28di/28dj со стороны меню).
- R2-4 co-op кампании: недели-месяцы, ВЫСОКИЙ риск (скрипты кампании не тестировались в сети;
  миграция хоста, владение ИИ, сейв/респаун — всё надо синхронизировать).
- Сквозной убийственный риск (не изменился): нет эталона того, что co-op кампании FC3 вообще когда-либо
  работал; каждый этап валидируется лишь против нашей собственной реконструкции.

Итог: R2 — это **исследовательский проект масштаба недель-месяцев с высоким риском**, и его первый
гейт (реальная Storm listen-сессия офлайн) сам по себе неопределён, т.к. мы уже видели, что игра
ждёт онлайн-состояние сессии со стороны меню. R2-A/B — самый перспективный порядок, но считайте
этап R2-1 (есть ли вообще пригодный шов не-RV-провайдера?) решением go/no-go.

## 5. Рекомендация

Сначала сделать R2-1 и считать его жёстким гейтом. Если R2-1 найдёт чистый шов провайдера и базовый
провайдер может работать офлайн — идти к R2-2. Если R2-1 покажет, что `_RdV`-провайдер жёстко
прописан и базовый не может стоять отдельно — остановить R2; оставшийся путь только стратегия D
(полная эмуляция co-op-бэкенда RendezVous), а она строго больше. Тем временем mod-262 SOLO остаётся
единственным рабочим co-op FC3.


## 6. РЕЗУЛЬТАТЫ R2-1 (сессия 28dx; полный Ghidra-анализ сделан)

Подтверждено авто-анализом (NOTES 28dx): обе группы провайдеров и операций присутствуют с
синглтонами-регистраторами имён: базовый `CGameMatchmakingProvider` 0x1158922c / `_RdV` 0x1158b438 /
`CSessionMatchmakingProvider` 0x11589210; `CSessionCreateOperation` 0x11523fa8 (init FUN_10425868) /
`_RdV` 0x11527a78; `CSessionJoinOperation` 0x11524030 / `_RdV` 0x11527b88; `CSessionSearchIPOperation`
0x11524014. Execute RV-создания = FUN_1044b2cb это слот vtable (лишь DATA-ссылка с 0x11527a64,
0 E8-коллов), гейтится FUN_1042c988(this)=*(this+0x3c)!=1,3. Полная схема параметров в FUN_1061e581
(NetEngineType id 0x3c, MatchMakingEnabled 0x4d, SessionType 0x38, SearchIdAddress 8, JoinGame 0x53,
JoinService 0x54, JoinSessionId 0x18, PlaylistId 0x34, SearchSlots 0x48). Дев-парсер CLI FUN_107ab377
разбирает -keyonline (ключ "a123456"), -login x4 + -password x4, -splitscreen (4-слотная таблица, шаг 0x24).

GO/NO-GO: GO (с оговоркой). Не-RV шов есть, LAN-схема параметров полноправна. Открыто: доказать, что
базовый провайдер строит Storm LAN-сессию. ДАЛЕЕ = R2-1b: (1) найти место конструкции/установки
`CGameMatchmakingProvider_RdV` (заменить на базовый `CGameMatchmakingProvider`), (2) декомпилировать
базовый `CSessionCreateOperation::Execute` и подтвердить открытие Storm-сессии на портах 9000-9004.


## 7. РЕЗУЛЬТАТЫ R2-1b (сессия 28dy) - Стратегия A ИСКЛЮЧЕНА

Найдены установка провайдера и обе vtable. Конструкторы пишут vtable провайдера: КОНСТРУКТОР базового
CGameMatchmakingProvider FUN_1077ac7e пишет 0x11589198 (базовая vtable); КОНСТРУКТОР CGameMatchmakingProvider_RdV
0x10786c8d пишет 0x1158b458 (vtable RdV, на 0x10786c94); синглтон RdV 0x11e684e8 строится инициализацией
провайдеров 0x10786c5c, которая регистрирует базовый провайдер и наслаивает RdV через FUN_1008bf50. Точка
подмены = патч 0x10786c94 (или рантайм-подмена vptr у 0x11e684e8). НО виртуалы базовой vtable провайдера
0x11589198 - АБСТРАКТНЫЕ ЗАГЛУШКИ (return 0x12/0x3e/0x3f/1, пустые деструкторы); create/join не реализованы.
=> Стратегия A мертва: подмена на базовый даёт заглушки-ошибки. Рабочего не-RV провайдера в бинарнике нет.
R2 теперь = (B') написать с нуля LAN-провайдер, реализовав весь интерфейс vtable провайдера + Storm create,
либо (D) полная эмуляция RendezVous. Якорь установки самописного провайдера: vtable 0x1158b458 / синглтон
0x11e684e8 / ctor 0x10786c8d.
