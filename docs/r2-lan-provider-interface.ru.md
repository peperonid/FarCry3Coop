# Спецификация интерфейса `CGameMatchmakingProvider` — что должен реализовать LAN-провайдер (путь R2 B')

Основа: vtable поставляемого `CGameMatchmakingProvider_RdV` по VA образа **0x1158b458** (синглтон RdV
0x11e684e8, конструктор 0x10786c8d). Базовая vtable `CGameMatchmakingProvider` = 0x11589198 (её виртуалы -
абстрактные заглушки; см. NOTES 28dy - НЕ переиспользовать). Самописный LAN-провайдер = новая vtable формы
0x1158b458 + её установка (патч записи vptr на 0x10786c94, либо рантайм-подмена vptr синглтона 0x11e684e8).

Все адреса - VA образа (добавлять базу модуля в рантайме; ASLR). x86 __thiscall: `ecx` = `this` провайдера;
доп. аргументы кладутся справа налево. "Слот" = индекс в vtable (смещение = слот*4).

## Что реально должен реализовать рабочий LAN-провайдер

Сетевое поведение сосредоточено в **5 слотах: 5, 13, 15, 16, 17** (плюс событийная обвязка 22/23 и жизненный
цикл 0/1/6/7/21). Слоты 3,4,8,9,10,11,12,14,18,19,20 можно оставить как поставляемые тривиальные заглушки.

- **Слот 15 CreateSession** — вместо FUN_107925a8 (строит RV/GATOR-запрос) открыть **Storm listen-сессию** на
  портах 9000-9004 и опубликовать локальный дескриптор сессии (имя/слоты/playlist). Возвращать true при успехе.
  Самый важный метод для переписывания.
- **Слот 13 join/поиск по id** — вместо FUN_11279ae0 (RV-rendezvous-запрос с асинхронным callback
  PTR_FUN_1158b460 + таймаут) делать LAN-обнаружение (в движке уже есть `storm::echo::lan` /
  `BroadcastLanDiscovery2`) и резолвить id в локальный хост, затем отдать через тот же контракт callback.
- **Слот 5 диспетчер** — замаппить коды create/join/search игры (матрица {1,5,1000} x {0,1,2}) на ваши
  Storm-операции; сохранить тот же контракт входа, чтобы вызывающие выше работали.
- **Слоты 16/17 перечисление** — возвращать свои списки сессий/игроков ровно в тех выходах (шаг 0x1c для сессий
  с показанным маппингом состояний; шаг 0x10 для игроков). Это читает UI/лобби.
- **Слоты 22/23 наблюдатели** — сохранить семантику вектора; игра получает через них события join/результат/
  ошибка, поэтому ваши Storm-события сессии должны приходить в зарегистрированных наблюдателей.
- Глобал менеджера сессий `*0x11e42c90` (используется слотами 5 и 13 через vtable+0xc) - это онлайн-менеджер
  сессий FCX; LAN-провайдер должен либо держать его достаточно живым для этих вызовов, либо их обходить. Это
  тот же объект online-service, гейтивший всё в NOTES 28dj-28dq - так что B' не отменяет тот гейт, а переносит
  проблему в эти 5 методов.

## Объём / риск (спецификация не меняет оценки, но делает её конкретной)

- Интерфейс из 24 слотов, ~5 сетевых методов + жизненный цикл + события для написания против недокументированного
  ABI vtable; путь создания обязан корректно вести `storm::echo` создание сессии офлайн (порты 9000-9004) И
  удовлетворить контракт менеджера сессий `*0x11e42c90`, от которого уже зависят вызывающие.
- Убийственный риск в силе: нет эталона, что FC3 когда-либо запускал не-RV-сессию, поэтому каждый метод
  валидируется против нашей собственной реконструкции. Рекомендован один спайк: реализовать минимально
  15+13+5+22/23, установить через подмену vptr на синглтоне 0x11e684e8, и проверить, появится ли Storm
  listen-сессия на 9000-9004 - это и есть go/no-go для всего пути B'.
