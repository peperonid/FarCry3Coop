# Путь A — эмуляция локального фейк RendezVous / GATOR session-сервиса для ко-опа Far Cry 3 (статический план)

> Статус: **разведка / план** — ради этого документа игра не запускалась, бинарь игры не менялся.
> Суть: что нужно построить, чтобы каскад ops ко-опа кампании завершился против **локального
> фейк-сервера** вместо живых сервисов Ubisoft, а затем передал управление нативной `storm::echo`
> LAN-сессии (фактическому транспортному слою игры). Это единственный оставшийся путь после того,
> как все рычаги на уровне хуков были опровергнуты живьём (см. `NOTES.ru.md`, сессии 28bd / 28be).
> Точные внутренние литералы (пути сборки Ubisoft, хост online-конфига в рантайме, FQDN
> краш-телеметрии) здесь намеренно **не** приводятся; они есть в `NOTES.ru.md` (сессии 28bc, 28be)
> и не должны попадать в публичный PR.

[English version](coop-gator-emulation-plan.md) · Русский (этот файл)

## 1. Почему это единственный оставшийся путь

Действие Host в ко-опе кампании жёстко привязано к пути UbiAuth + RendezVous/GATOR:
- Op входа (`FUN_11279f90`, vtable op по RVA `0x116cf86c`) всегда выполняет RendezVous/UbiAuth
  логин; для ко-опа кампании **нет ветки NetEngineType** в LAN-бэкенд (`NOTES` 28aq / 28bc).
- Живые пробы доказали, что игра реально **отправляет RV-логин и получает колбэк**
  (`RVLOGIN-SEND` / `RVLOGIN-CB`), т.е. ко-оп-поток общается с сетевым сервисом и не отстреливается
  заранее (`NOTES` 28bd).
- Но углубление в реальный RV session-поток **крашится**, даже когда наши хуки нейтрализованы, —
  крашит собственная глубокая RV/GATOR-обработка игры, а не наш код (`NOTES` 28be).

Вывод: патчить клиент хуками ниже каскада UbiAuth/RV → установления сессии GATOR нельзя. Чтобы
хостить/входить в ко-оп сессию кампании, нужно заставить клиент верить, что он говорит с настоящим
RendezVous/GATOR сервисом, — т.е. **эмулировать этот сервис локально**, удовлетворив весь каскад
result-событий ops, а затем позвать клиенту поднять его собственный `storm::echo`-session для самой
игры.

## 2. Инвентарь находок (статика)

Все адреса — RVA (плюс базис модуля в рантайме; ASLR активен). Внутренние префиксы путей сборки
Ubisoft и литеральный FQDN online-конфига держим только в `NOTES.ru.md`.

| Находка | О чём говорит |
|---|---|
| `prudp:/`, `prudps:/`, `prudp`, `prudps` (`.rdata`) | Транспорт — **PRUDP** (UDP-база, надёжный слой). `prudps` = защищённый/шифрованный вариант. Есть блок счётчиков PRUDP-пакетов (надёжная передача / ретрансмиссия) → полная реализация PRUDP статически слинкована. |
| `getaddrinfo`, `freeaddrinfo`, `getnameinfo`, `WSASocketA`, `WSASendTo`, `WSARecvFrom`, `WSAIoctl`, `WSACreateEvent`, `WSAWaitForMultipleEvents`, `WSAGetOverlappedResult` (импорты WS2_32) | RV сокет-драйвер резолвит хост через **`getaddrinfo`** и делает UDP I/O через **overlapped `WSASendTo`/`WSARecvFrom`**. Эти именованные импорты перехватываются на IAT — чистая точка перехвата. |
| `onlineconfigservice.ubi.com` + варианты `cert-` / `uat-` | FC3 получает **онлайн-конфиг по HTTPS**; эндпоинты RendezVous/GATOR выдаются в рантайме этим конфиг-сервисом, а не зашиты в бинарь. Отсюда отсутствие статического RV-хоста. |
| `clusterResId` | RV-сессии размещаются в **кластерах**; маршрутизация кластеров идёт из конфига. |
| `CRendezVousLoginOperation`, `CRendezVousLocalizationOperation`, `CRendezVousConfigureUPnPOperation`, `CSessionCreateGameOperation`, `CSessionSearchOperation`, `CSessionAcceptInviteOperation`, `COnlineGameConfigOperation`, `CSessionCreateOperation(_RdV)`, `CGameMatchmakingProvider(_RdV)` | **Каталог ops**, которые клиент прогоняет при подъёме ко-опа (см. §4). |
| `JobUbiAuthenticationLogin`, `JobLaunchUPnPThread` (+ `ThreadPerformUPnP`, `StepCheckForCompletion`) | Async **jobs** за ops логина и UPnP. |
| UPnP-строки: `InternetGatewayDevice:1`, `WANIPConnection:1`, `WANPPPConnection:1`, `upnp:rootdevice` | При хостинге клиент открывает **UPnP-проброс**; фейк должен терпеть UPnP (или UPnP заглушается/падает мягко). |
| `DummyUbiUser@quazal.com` / `UbiDummyPwd` | RV гостевой логин использует заглушку-креды → клиент может дойти до RV-логина без полностью аутентифицированного Ubi-пользователя (подтверждено живьём: отправляет + получает колбэк). |
| `127.0.0.1`, `0.0.0.0` присутствуют | Есть loopback/wildcard-привязки → локальному фейк-серверу не нужен особый стек. |

## 3. Архитектура перехвата (где сидит фейк)

Две подзадачи: (а) заставить RV-трафик клиента попасть на наш фейк; (б) говорить по протоколу и
генерировать нужные результаты.

**(а) Редирект RV → localhost.** Самая нижняя чистая точка — **`getaddrinfo`** в IAT WS2_32 (прокси
уже в процессе через автозагрузку лоадера, `NOTES` 28ai). Стратегия:
- Хукнуть `getaddrinfo` в прокси. Для RV/GATOR-хостов, возвращаемых online-конфиг сервисом,
  возвращать `127.0.0.1` вместо разрешённого адреса Ubisoft; остальное пропускать насквозь.
- Страховка: хукнуть `WSASocketA`/`WSASendTo`/`WSARecvFrom`, чтобы (i) форсить назначение
  `127.0.0.1:<порт фейка>` и (ii) логировать точные PRUDP-фреймы для RE.

Это обходит runtime-хост конфигов целиком — фейкодить HTTPS/TLS `onlineconfigservice` **не нужно**,
т.к. мы редиректим после резолва. (Альтернатива — фейк HTTPS конфиг-сервис — требует доверия к сертy
или хука до TLS и строго сложнее; не делать.)

**(б) Локальный PRUDP/GATOR сервер.** Небольшой UDP-листенер на `127.0.0.1:<порт>`, который:
- декодирует PRUDP-пакеты (заголовок, надёжное кадрирование ack/reliable, ping/pong, фрагментация),
- демультисплексит вызовы прикладных сервисов внутри,
- отвечает результатами, которые ждёт каскад ops клиента (§4),
- в итоге возвращает инфо об адресах/пирах, достаточное, чтобы клиент поднял `storm::echo`-сессию.

## 4. Каскад ops, который нужно удовлетворить

Реконструкция порядка (на стороне клиента, по классам ops + живому трейсу логина). Каждый op
завершается, когда клиент публикует **result-событие** для него; фейк обязан выдать эти результаты.

1. `COnlineGameConfigOperation` / загрузка online-конфига — обычно с HTTPS конфиг-сервиса. С
   редиректом `getaddrinfo` мы это в основном пропускаем, но клиент может ждать blob игрового
   конфига (плейлист, макс. игроков, правила). **Неизвестно:** нужен ли ко-опу успешный config-op
   или он терпит кэшированный/пустой.
2. `CRendezVousLoginOperation` (за ним `JobUbiAuthenticationLogin`) — **подтверждено, что идёт и
   получает колбэк живьём**. Фейк должен ответить успешным RV-результатом «connected / logged-in»
   (тикет / session ticket, который клиент примет). Эту часть мы наблюдали (`RVLOGIN-*`), но точный
   успешный payload пока не снят (`NOTES` 28be: STATUS не прочитан).
3. `CRendezVousConfigureUPnPOperation` (`JobLaunchUPnPThread`) — при хостинге открывается UPnP-маппинг.
   На фейк-пути UPnP можно дать просто падать/пропускаться (много RV-клиентов идут с фолбэком
   публичного адреса). **Неизвестно:** требует ли жёстко путь хоста ко-опа успешного маппинга.
4. `CRendezVousLocalizationOperation` — размещает пользователя/сессию в кластере. Фейк возвращает
   результат кластера/локализации (маршрутизация кластера обычно из конфига).
5. `CSessionCreateGameOperation` (хост) / `CSessionSearchOperation` (вход/просмотр) /
   `CSessionAcceptInviteOperation` (принять) — **подъём сессии**. Это ядро: фейк обязан создать/вернуть
   дескриптор сессии (id сессии, адрес+порт хоста, список пиров и любой `session ticket`/атрибуты,
   которые валидирует клиент).
6. **передача в storm::echo** — когда RV-слой передал клиенту дескриптор сессии с адресами пиров,
   клиент поднимает нативную `storm::echo` игровую сессию. Этот слой данных **локальный / LAN /
   loopback** и НЕ работа нашего фейка, — но наш фейк обязан подать дескриптор, при котором он
   свяжется с настоящими пирами (другими инстансами игры). Это и награда всего подхода, и главный
   неизвестный: как RV-дескриптор сессии ложится на подъём storm::echo-сессии (`NOTES` 28ay: ко-оп
   использует `join_handler`, а не `host_handler`).

**Result-события / поля payload известны лишь частично.** Имена классов ops и трейс логина
обоснованы; точная wire-схема каждого результата (раскладка полей, содержимое `session ticket`,
дескриптор кластера) ещё **не** отре. Именно снятие этого — основная работа первых стадий сборки.

## 5. Декомпозиция, результат, риск, трудоёмкость

Усилие = сфокусированные недели одного сильного RE/разработчика; диапазоны предполагают наличие
публичного PRUDP-референса для кадрирования (Ubisoft Connect PRUDP публично задокументирован и,
возможно, делит кадрирование пакетов со игровым RV-стеком — проверять, не предполагать). Риск =
может ли стадия поставить весь путь на мёртвую точку.

| Стадия | Результат | Риск | Усилие |
|---|---|---|---|
| **S0. Снимок PRUDP на проводе** | Прокси-хуки `WSASendTo`/`WSARecvFrom`/`getaddrinfo`; снять **реальные** PRUDP-фреймы подъёма ко-опа против живых серверов (1 хост + 1 вход, интернет ВКЛ). Дать лог фреймов + использованный хост/порт. | Средний (не должен крашиться; путь съёма прозрачен) | **1–2 нед** |
| **S1. Кодек PRUDP** | Раскодировать/закодировать PRUDP-заголовок + надёжное кадрирование + ping/pong из снимка S0. Прогнать снятую сессию офлайн туда-обратно. | Высокий (шифрование/подпись prudps) | **2–4 нед** |
| **S2. Редирект на фейк** | `getaddrinfo`→`127.0.0.1`; фейк UDP-листенер на снятом порту; клиент доходит и начинает PRUDP-рукопожатие. Клиент не должен крашнуться на рукопожатии. | Средний | **1–2 нед** |
| **S3. Ops логина + локализации** | Фейк отвечает результатами `CRendezVousLoginOperation` + `...Localization`, чтобы клиент сообщил RV connected. | Высокий (точная schema результата) | **2–3 нед** |
| **S4. Create/search сессии + дескриптор** | Фейк возвращает дескриптор сессии, удовлетворяющий `CSessionCreateGameOperation`/`CSessionSearchOperation`/`CSessionAcceptInviteOperation`. Клиент доходит до «session joined» без краша. | **Наивысший** (session ticket / маппинг пиров / что потребляет storm::echo) | **3–5 нед** |
| **S5. Подъём storm::echo на 2 пирах** | Два инстанса игры, каждый редирекчен на фейк; после S4 оба получают дескриптор пира и стартуют storm::echo **друг против друга** (loopback/LAN). Реальный go/no-go. | **Экстремальный** (вся теория на этом) | **2–4 нед** |
| **S6. 3–4 игрока + надёжность** | Расширить дескрипторы на 4 пира; потеря пакетов/поздний вход; воспроизводимость. | Высокий | **2–4 нед** |

**Итого: ~13–24 сфокусированные недели, доминируют S1 (крипто PRUDP), S4 (schema сессии) и S5
(передача storm::echo — единственный решающий неизвестный).** Эти же три места — где путь может
умереть окончательно, даже когда остальные стадии прошли.

## 6. Ключевые риски и открытые неизвестные

- **Шифрование/подпись prudps** — защищённый вариант PRUDP требует ключ/схему подписи пакетов.
  Публичный PRUDP Ubisoft Connect может покрывать auth, но **не** игровой канал GATOR-сессий. Если
  игровой канал использует другой ключ/соглашение, S1 может стать намного сложнее или блокируема.
- **Зависимость от online-конфига** — некоторым ops может быть нужен непустой blob конфига/кластера;
  если клиент отвергает отсутствующий, придётся фейкодить и этот payload (не HTTPS-транспорт, а
  декодированный blob).
- **Содержимое session ticket** — `NOTES` 28x/28z: session ticket минтится сервисом и (для
  наблюдаемого пути) на MD5 без асимметричного ключа — ободряюще, но точный набор полей, который
  валидирует клиент, ещё неизвестен.
- **Маппинг storm::echo (S5)** — гвоздь: даёт ли RV-дескриптор сессии клиенту открыть storm::echo
  на произвольные выбранные нами пиры? Если storm::echo сам валидирует тикет/ownership против живого
  авторитета, путь рушится на последнем шаге.
- **Жёсткое требование UPnP** — если хостинг отказывается идти без успешного проброса, фейк обязан
  удовлетворить и UPnP (или заглушить завершение UPnP-задачи).

## 7. Рекомендуемый порядок и де-рискование

1. Сначала дёшево сделать **S0 (съём)**: отвечает «какой хост/порт + как выглядят фреймы», снимает
   риск с S1 и стоит мало. Нужна одна живая 2-инстансная ко-оп попытка (интернет ВКЛ) с хуками
   съёма — первая стоящая вещь, если этот путь выбран.
2. Перед S1 **сверить публичный PRUDP-референс** со снимком S0 (доля кадрирования/ключей) — это
   ограничивает стоимость S1.
3. **Как можно раньше де-рисковать S5 концептуально** (он kill-switch): когда научимся декодировать
   реальную 2-игроцкую ко-оп сессию (S0/S1), изучить дескриптор сессии / аргументы подъёма
   storm::echo, чтобы подтвердить: клиент подключится к указанным нами пирам. Если storm::echo нужен
   живой авторитет — бросить путь до постройки S3/S4.
4. Только затем строить S2→S4 по порядку, проверяя, что клиент доходит до следующего ops.

## 8. Связь с живым стендом проб

Все S0/S2 используют существующие прокси-в-процессе + шим (`src/uplay_proxy`, `src/coop_shim`;
автозагрузка через прокси лоадера, `NOTES` 28ai; detached-запуск через WMI). Новая работа — (а)
хуки `getaddrinfo`/Winsock IAT, добавленные в прокси для съёма/редиректа, и (б) отдельный бинарь
локального PRUDP-сервера (новый компонент `tools/`). Никаких записей в бинарь игры на любой стадии.

## 9. Итог

Путь A **принципиально выполним, но дорог и подпирается двумя жёсткими неизвестными** (крипто
игровой PRUDP-сессии в S1 и маппинг пира storm::echo в S5). Самая ценная дешёвая вещь — если
владелец вообще решит вкладываться — это **S0: снять реальный трейс подъёма 2-игроцкой ко-оп
сессии**, что превращает большинство допущений выше в факты и ограничивает остальную оценку. Если
«1.05 LAN» ко-оп Bantila окажется работающим **ниже** слоя GATOR (см. PR #1), он может обойти всю
эту постройку целиком; стоит подтвердить это до вложения недель.
