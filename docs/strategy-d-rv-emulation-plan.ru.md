# Стратегия D — локальный эмулятор RendezVous/NetConnect-бэкенда для Far Cry 3: план + оценка

Отдельный план. Предпосылки: NOTES 28cw/28cx/28cz (PRUDP v1 + задел RV), 28dq/28do (офлайн co-op
хост использует storm::echo, а не RV; FCX ждёт события online-service/party/session), 28ea (create/search
провайдера уходят в RPC-клиент NetConnect/RV), docs/r2-lan-provider-interface.md. Задел: `scripts/rv_server/`
(PRUDP v1 кодек, `rv_server.py` handshake + RMC-диспетчер, `config_server.py` шов SandboxUrl, `test_prudp.py`).

## 0. Что такое D и модель слоёв (точно)

Онлайн co-op FC3 на PC сидит на ДВУХ слоях Ubisoft/Quazal; D нацелен на нижний:
1. **FCX online-слой** (в `FC3_d3d11.dll`): машина состояний логина (28db/28dd), оркестрация
   party/matchmaking, и состояние «online-service connected», гейтившее всё (28dq). Из-за него OW15
   давал «servers unavailable» (28dm).
2. **Quazal NetConnect / RendezVous-слой** (блок `0x112xxxxx` + `storm::echo`): реальный сервис
   rendezvous + сессии + тикета, куда игра звонит по PRUDP/RV на URL из OnlineConfig
   (`SandboxUrl = prudp://address=…;port=…`). `CGameMatchmakingProvider_RdV` create/search (слоты
   провайдера 15/13 → `FUN_107925a8` → `FUN_11258f20` и `FUN_11279ae0` → `FUN_11279920`, 28ea) говорят
   RMC-поверх-PRUDP с этим сервисом. `storm::echo` — игровая плоскость данных (UDP:9000-сессия co-op
   хоста, 28do).

**Премис D:** поднять локальный сервер, отвечающий NetConnect/RV-сервису, куда звонит игра, чтобы её
RendezVu-клиент аутентифицировался, создал/нашёл сессию и обменялся тикетом сессии, после чего два
игровых клиента соединятся по storm::echo. D заменяет МЁРТВЫЙ Ubisoft RV/GATOR-бэкенд.

**Центральная неизвестность, определяющая всю D (из 28dj/28dq):** в каждом офлайн net-on тесте клиент
FC3 НИ РАЗУ не послал RV-дозвон (RV-PROBE = 0). Он формировал лишь локальную storm::echo-сессию для
co-op-хоста, а иначе ждал состояния FCX online-service. Значит прежде писать RV-сервис надо ответить:
**можно ли вообще завести FC3 на дозвон RV-серверу и при каком состоянии FCX?** Если нет — у D нет
точки входа и она бессмысленна. Поэтому этап 0 ниже — это эксперимент-захват, а не фича сервера.

## 1. Что уже работает (офлайн, протестировано, без игры, без C:)

Из `scripts/rv_server/` (этап S1):
- `prudp.py`: пакет PRUDP **v1** `decode/encode`, опции (`id, (type<<4|size), value`, LE),
  SYN/CONNECT/DATA/PING/DISCONNECT, терпимый парсер. Сигнатура/чек-сумма заголовка — ЗАГЛУШКА.
- `rv_server.py`: UDP-сервер, машина `SYN → CONNECT(+connid) → CONNECT-ack → DATA`; hex-лог каждого
  пакета; диспетчер `services[(protocol_id,method_id)] → handler` по RMCMessage-полезной нагрузке.
- `test_prudp.py`: офлайн-доказательство — round-trip кодека + синтетический клиент, завершающий
  handshake и RMC request/response. Печатает `ALL OK`.
- `config_server.py`: отдаёт OnlineConfig с `SandboxUrl → prudp://address=127.0.0.1;port=50000`
  (шов конфига, направляющий клиента к нам).

Нет: prudps (шифрованный) транспорт; реальные ID опций RV (conn-id/pid/cid — догадки по таблице NEX);
любой реальный RV-сервис (auth, create, search, ticket). Все RV protocol/method ID **неизвестны**
(нет эталонного захвата).

## 2. Что предположительно вызывает игра (статика + пробел)

Из цепочки RV-подключения (28cq) и низа провайдера (28ea) клиент вызывает по порядку:
- **ConnectEndPoint / DNS + SYN** на host:port из `SandboxUrl` (Quazal `JobConnectEndPoint`).
- **ConnectToAuthenticationService** (`FUN_11252f70`, 28cq): сервис RV/NetConnect **login/auth**
  (`RendezVousBackEndServices` / `JobBackEndServicesLogin`). При успехе менеджер строит RV-саб-объект
  (`this+0x110`, `FUN_1041f965`, 28cp), т.е. «online-service connected».
- **RegisterURLs / CompleteConnect** (строки `BackEndServicesConnect::*`, 28da): регистрация URL сервисов.
- **Session create** (слот 15 → `FUN_107925a8` → финал `FUN_11258f20`): RV CreateSession RMC.
- **Session search / join-by-id** (слот 13 → `FUN_11279ae0` → `FUN_11279920`): RV search RMC, async callback.
- **Перечисление игроков/сервисов** (слоты 16/17), **add/remove наблюдателя** (22/23).
- **Ticket / GameSessionKey**: обязателен для допуска двух клиентов в одну игровую сессию
  (античит-ключ сессии). Его сообщения в том же RV RMC-слое; НЕ локализованы (достигаются только после
  успеха create/search).

**Пробел:** конкретные RV `protocol_id/method_id`, их бинарные разметки req/resp, prudps key-exchange и
формат тикета не подтверждены — всё это жило только в (мёртвом) RV-сервере Ubisoft. **Нет open-source
Quazal RendezVous-сервера эпохи FC3** и **нет эталонного FC3 RV-захвата** (28dq/28ds). В этом вся
сложность D.

## 3. Формат PRUDP / prudps

- PRUDP v1 транспорт: реализован (S1). Магия `EA D0`, на пакет seq/session/substream/source/dest,
  TLV-опции. Достаточно для handshake.
- **prudps (`s` в `prudp://...`)**: RC4 + HMAC шифрование нагрузки с сессионным ключом, устанавливаемым
  при CONNECT (Quazal использует подписанный «connection keyblock» — RSA на ключе сервера + DH/производный
  сессионный секрет). У нас НЕТ приватного RSA-ключа RV-сервера FC3 и формата keyblock, и FC3 может
  верифицировать ключ сервера. Два пути: (a) отдавать чистый `prudp` (без шифрования), если клиент примет
  не-безопасную схему через шов конфига, или (b) восстановить логику key-exchange/verify из клиента
  (блок NetConnect) и либо дать совместимые ключи, либо запатчить клиент пропускать верификацию.
  **Это трудная неизвестность на несколько дней в обоих случаях.**

## 4. auth / party / session / ticket — что подделывать

- **auth (login)**: FCX передаёт креды из (проксируемого) лаунчера (28db/28dd); при
  `FC3COOP_FAKE_CREDS=1` структура кредов фабрикуется. Локальный RV-auth должен принимать фабрикованные
  креды (без валидации Ubisoft passport) и вернуть корректный login OK с player id / service master.
  Попробовать можно, но точная разметка ответа неизвестна.
- **party**: co-op-хост фактически односессионный; FCX может требовать состояния party/лидера.
  Перечисление провайдера (слоты 16/17) и наблюдатели (22/23) — как UI читает игроков; локальная сессия
  должна заполнять эти списки, чтобы лобби показывало слот для входа.
- **session**: RV create/search/ticket, позволяющие клиенту B найти и войти в сессию клиента A, затем
  передающие storm::echo плоскость данных. Нужны реальные разметки create/search/ticket (неизвестны).
- **ticket / GameSessionKey**: должен производиться RV-сервисом и приниматься античитом обоих клиентов;
  вероятно, самая трудная неизвестность (крипто, верифицируется клиентом).

## 5. Поэтапный план с гейтами + критериями остановки

**Этап D0 — решающий эксперимент-захват (делать первым; ~1-2 сессии; МАЛО кода, МНОГО инфы).**
Вопрос: можно ли завести FC3 на дозвон RV-серверу и пошлёт ли он NetConnect auth-RPC?
Метод: net-on конфиг БЕЗ fake-online (рецепт 28di), `SandboxUrl → prudp://127.0.0.1:50000`
(config_server), rv_server + RV-PROBE + FCX login-пробы; довести игру до co-op и логировать весь UDP.
- Гейт A: хотя бы один PRUDP SYN доходит до rv_server и handshake завершается до `established`.
  - PASS → FC3 умеет звонить RV локально; идти к D1 (и прежний вывод «FCX ждёт party/session»
    уточняется: онProceed дальше, когда RV-auth отвечает).
  - FAIL (ноль входящих, как видел 28dj) → **СТОП D**: флоу co-op FC3 не звонит RV, эмулировать некуда;
    единственный офлайн co-op путь — storm::echo (28do), т.е. путь подмены провайдера (B', сам заблокирован — 28ea).
    Записать и остановиться.
Этот этап превращает D из спекуляции в заведомо-решаемый или заведомо-мёртвый путь прежде написания
сервиса. Всё ниже условно от PASS D0.

**Этап D1 — prudps-транспорт (дни-недели).** Получить входящий RMC DATA-кадр, дешифруемый в что-то
разбираемое, и отправить корректный шифрованный ответ. Гейт: клиент принимает CONNECT + первый
шифрованный ответ и не отключается (нет немедленного DISCONNECT / цикла ретраев). Стоп: если prudps
пинит RSA-ключ, который мы не воспроизводим, и клиент жёстко валит верификацию ключа, D мертва, если
только не запатчить клиент на `prudp` (без шифрования) — оценить этот фолбэк.

**Этап D2 — сервис auth/login (дни-недели).** Реализовать RMC-ответ ConnectToAuthenticationService, чтобы
FCX отметил online-service connected и построил RV-саб-объект. Гейт: FCX login залипает И RV-саб-объект
ServiceMaster (`this+0x110`) становится non-null (наблюдается существующим shim MGR_WATCH/observer).
Стоп: если разметку ответа login не удаётся реверсануть из парсера NetConnect-клиента (читать, как клиент
парсит наш ответ, вести к «malformed», пока не изучим формат), и за неделю прогресса нет — эскалация в
полный реверс расметки пакетов (большой объём).

**Этап D3 — session create/search/ticket (недели-месяцы).** Реализовать RV CreateSession + Search +
GameSessionKey/ticket, чтобы два клиента встретились через rv_server и запустили storm::echo-сессию.
Гейт: два инстанса FC3 в одной LAN встречаются через rv_server, обмениваются тикетом, и формируется
storm::echo-сессия с обоими игроками (наблюдать storm::echo::session AddPlayer + перечисление слота 17
показывает 2). Стоп: если тикет/GameSessionKey не удаётся сделать приемлемым античиту клиента, два
клиента не войдут в одну сессию → D мертва.

**Этап D4 — QA co-op кампании (недели-месяцы).** Когда два человека в мире — прогнать харнесс
desync/ownership/chaos (хабовские `tools/`) и проверить, что скрипты кампании терпят co-op. Гейт: честный
2-ботовый QA-прогон. (Тот же этап, что R2-4; не зависит, пришли мы через B' или D.)

## 6. Объём / риск / рекомендация

- D0: дёшево и решающе — **делать в любом случае**, заодно чисто перепроверяет вывод о тупике B'.
- D1-D3: **командномасштабно, месяцы**, на неизвестностях, которые нельзя ограничить без трафика:
  крипто prudps (RSA/keyblock, которого у нас нет), каждая разметка RV RMC-сообщения, и ticket/GameSessionKey.
- Убийственный риск (не изменился и решающ для D): **нет эталонного референса.** Open-source
  Quazal RendezVous-сервера эпохи FC3 нет, а трафик FC3 RV рождался только против (мёртвого) сервера
  Ubisoft, который мы так и не сняли живым. Каждую разметку сообщений надо выводить допросом парсера
  клиента вслепую.
- **Рекомендация:** сначала D0. Если D0 покажет, что FC3 не звонит RV — остановить D (и B') — остаётся
  только mod-262 SOLO. Если D0 неожиданно PASS, следующий go/no-go — D1 (prudps); фиксироваться там,
  только если key-exchange выглядит восстановимым. По текущим данным (28dj: RV-PROBE ноль на реальном
  co-op-хосте) априори D0 провалится, поэтому считайте D маловероятной, а mod-262 SOLO — артефактом.


## 7. РЕЗУЛЬТАТ D0 (выполнено 2026-11-17): **FAIL**

Чистый валидный прогон (после починки двух багов харнесса: запущенная игра блокировала loader, а
повышенная оболочка разрешала голое `python` в документ system32). Когда харнесс заведомо жив:
- прокси живой (UPLAY-очередь событий логируется из `FC3_d3d11.dll`), шим живой (RV-PROBE/MGR_WATCH/
  login-хуки поставлены);
- FCX login дошёл и залип **LoggingIn(6) -> LoggingInSucceeded(9) -> 13/14**, без цикла 15
  (LOGOUT-BLOCK сработал ~60k раз = движок постоянно пытался разлогиниться, заблокирован);
- глобал online-менеджера сессий `DAT_11e42c90` NON-NULL (`0x44a8bbb0`, менеджер есть, но в простое);
- shim DNS-REDIRECT стоит (`onlineconfigservice.ubi.com -> 127.0.0.1` на IAT-слоте `getaddrinfo`).

**Решающий итог: FC3 вообще не вошла в RV-клиент.**
- `rv_capture.log`: **0** пакетов (ни SYN, ничего не дошло до `:50000`).
- shim **RV-PROBE в рантайме: 0** (залогируется только баннер установки; внутрипроцессные пробы
  RV connect/send ни разу не сработали).
- `uplay_api.log`: **0** `SetGameSession` / `CreateGameSession` / `ConnectToAuthenticationService` /
  `GetFriendList` / `IsPartyLeader`.

Это не зависит от значения конфига: RV-PROBE стоит на функциях RV-клиента *внутри* FC3, поэтому ноль
там означает, что код-путь RV не достигается независимо от того, куда указывает `SandboxUrl`.
Ожидание co-op «connecting to servers» гейтится **выше** RendezVous — на состоянии FCX
online-service / party-session (NOTES 28dp/28dq).

**Вердикт: Стратегия D мертва, и Стратегия B' делит тот же гейт, значит тоже мертва** (28ea:
B' упиралась в те же NetConnect/RV-недра, до которых FC3 не доходит). Критерий остановки этапа D0
(«ноль входящих + RV-PROBE не срабатывает => УБИТЬ D») выполнен. **Единственный рабочий co-op в
Far Cry 3 остаётся mod-262 SOLO (1 человек).** D1-D4 не продолжать.
