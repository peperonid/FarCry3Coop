# Условие A - нужно ли ПИСАТЬ в Ubisoft Connect (upc.exe / uplay_r14.dll на диске C:)?

Запись о решении + план патча. Статус: **рекомендую НЕ писать на C: сейчас** (см. «Рекомендация»).
Ни один файл на C: для этого решения не изменялся; анализ только на чтение. См. также
`docs/project-status.md`, сессии журнала 28cj/28ck/28cl/28cq/28cu/28cv/28cy.

## Что такое условие A
FC3 показывает «co-op сервис недоступен» исключительно из собственного онлайн LOGIN-СОСТОЯНИЯ игры
FCX (НЕ из обращения к серверу). Действие co-op Host FUN_10443663 возвращает «недоступно» ровно
когда синглтон онлайн-менеджера игры `DAT_11e42c90 == 0` (null офлайн). Чтобы заработал LAN-join
нескольких живых игроков, машине состояний логина FCX нужно дойти до `LoggingIn`, что запускает
`JobBackEndServicesLogin -> JobConnectEndPoint ->` RV (PRUDP) набор. Сейчас этого никогда не происходит.

## Ключевые факты, решающие вопрос о записи на C: (всё RE на чтение)
1. **Auth - это НЕ гейт Ubisoft-подписанного паспорта.** Логин FC3 - это сервис Quazal RendezVous
   UbiAuthentication поверх PRUDP с DUMMY-кредо из конфига (`DummyUbiUser@quazal.com` / `UbiDummyPwd`,
   ключ `h7fyctiuucf`). Мы контролируем ОБЕ стороны, поэтому наш RV-сервер принимает что угодно, что
   предъявит клиент; приватный ключ Ubisoft не участвует (28cj/28ck).
2. **Реальный upstream уже мёртв.** `public-ubiservices...?productId=46` лаунчера возвращает пустоту
   (серверное убийство, 28cv). Патч upc.exe не заставит мёртвый сервер выдать настоящий тикет, а
   игра его и не требовала.
3. **Весь вход, что шлёт upc.exe, уже приземляется на H:.** Игра <-> upc.exe говорят через именованные
   каналы (`PolledPipeSocket` + `PolledPipeProtoBufHandler<uplaydll@protocol@mg>`); игровой конец этого
   канала - наш прокси `uplay_r1_loader`, которым мы уже владеем и который патчим на H:.
4. **Поверхность присутствия аккаунта в загрузчике уже полностью подделываема и НЕ является гейтом.**
   Наш прокси форсит `UPLAY_USER_IsConnected == 1`, но игра ВСЁ РАВНО не продвигается и не вызывает
   API друзей/сессии/пати (28cu). Значит, «что upc говорит загрузчику» - не то, что нас блокирует.
5. **Вся цепь login->RV стоит внутри FC3_d3d11.dll (H:)** и это job-сантехника Quazal:
   - FUN_1041936b (вход online-init): строит менеджер (FUN_10420a77 -> DAT_11e42c90), затем дёргает
     онлайн-init операцию vtable+0x10 менеджера.
   - FUN_1127a0d0 (UbiAuthenticationClient.cpp): создаёт RV ServiceMaster в `manager+0x110` ТОЛЬКО
     после того как отложенная операция соединения в `manager+0x108` дойдёт до состояния 5 и пройдёт
     FUN_11237670.
   - FUN_11275f40 -> FUN_11279ba0 (гейт FUN_11245090) - путь endpoint/RV co-op Host.
   Ничто из этого не читает и не проверяет подпись Ubisoft-паспорта; это машины состояний, которые
   двигает сам FCX.

## Заключение
Ограниченная ЗАПИСЬ на C: (upc.exe / uplay_r14.dll Ubisoft Connect) **изменила бы только то, что upc
кладёт в канал, а игровой конец этого канала уже наш на H:.** Она не даёт никакого рычага, которого
нет на стороне H:, у auth нет подписи для проверки, а настоящий блокирующий триггер (предикат FCX,
решающий поставить в очередь операцию логина) живёт в FC3_d3d11.dll на H:. Патч на C: добавляет лишь
риск убить весь установочный лаунчер Ubisoft владельца (большой, с защитой от правок, общий для всех
игр Ubisoft) ради нуля новых возможностей.

## Рекомендация (моё согласие как агента)
Я НЕ даю согласия писать на C: сейчас, потому что анализ показывает: это цель не в тот слой.
Правильный следующий шаг - только на H::
- Найти предикат FCX, решающий поставить в очередь GatorLogin / продвинуть login-состояние мимо
  `FetchOnlineConfigRdy -> LoggingIn` (внутри FC3_d3d11.dll), то есть где FCX потребляет сигнал
  загрузчика помимо IsConnected (поле autologin / account-flags, а не просто bool).
- Эта точка потребления - на H: и есть настоящие ворота; удовлетворить её (или двигать операцию
  логина FCX прямо из coop_shim ПОСЛЕ понимания, почему неглубокий форс упал в AV в 28cg/28ci) - и есть путь.

## Если запись на C: когда-нибудь станет оправданной (держим как контролируемый план, НЕ выполняется)
Возвращаться только если будущий вывод на чтение докажет, что ЕДИНСТВЕННЫЙ недостающий вход нельзя
получить нигде, кроме как внутри upc.exe. Тогда и только тогда - с ОТДЕЛЬНОГО явного согласия
владельца по правилу AGENTS 2:
1. Сначала полный бэкап: скопировать весь каталог Ubisoft Game Launcher с C: на H: (по размеру,
   с проверкой хешей) до любого прикосновения.
2. Патчить КОПИЮ, никогда живой файл: собрать кандидат-патч uplay_r14.dll / upc.exe офлайн и тестить
   на одноразовой копии лаунчера, никогда на том, под реальным аккаунтом владельца.
3. Минимальный одиночный обратимый байтовый патч с письменным диффом до/после и однокомандным
   восстановлением из бэкапа; исходный хеш файла хранить в репозитории.
4. Никогда не патчить пути анти-тампера upc.exe; uplay_r14.dll (библиотека загрузчика) - меньшая и
   более безопасная цель, чем основной бинарник upc.exe.
И всё же ожидания близки к нулю: факты 1-5 выше говорят, что нужной возможности в этом файле нет.

## Что это решение НЕ меняет
- Mod-262 SOLO offline co-op остаётся зафиксированным рабочим результатом.
- Условие B (RV-эмулятор: кодек PRUDP v1 + handshake + скаффолд слоя RMC) остаётся построенным и
  покрытым тестами; его живой захват (S0) по-прежнему ждёт условие A.
